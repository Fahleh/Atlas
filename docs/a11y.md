> **Atlas Internal Documentation**

## Overview

Accessibility in Atlas is not a checklist — it is a design constraint applied from the start. Every interactive component is built to be operable by keyboard, navigable by screen reader, and visually clear at any contrast level. This document records the patterns, decisions, and known gaps across Atlas's component library.

Atlas targets **WCAG 2.1 Level AA** compliance.

**A note on scope, added during a July 2026 documentation pass:** this document was last substantively written in Week 5, before `EntityModal`, `StatusBox`, `Avatar`, `ProjectModal`, and the full delete/add-member/remove-member flows existed. Rather than re-documenting every new component from scratch — most of them are straightforward reapplications of the already-documented patterns below (another `role="alert"`, another `.srOnly` label, another `useFormStatus` submit button) — this pass adds only what's genuinely new or changed, and corrects one section that had gone stale (the timezone gap in Section 9, which was fixed but never updated here). Treat the Component Audit table (Section 8) as reflecting Week 5's components plus the specific additions noted, not as an exhaustive inventory of everything built since.

## 1. Core Principles

**Semantic HTML first.** The correct element is always preferred over ARIA. A `<button>` is better than a `<div role="button">`. A `<table>` is better than a grid of `<div>`s. ARIA is used to supplement semantics when native HTML falls short — never to compensate for using the wrong element.

**Every interactive element is keyboard-operable.** Click handlers are always accompanied by keyboard equivalents. No user flow requires a mouse.

**Focus is always visible.** `focus-visible` outlines are applied to every interactive element using `outline: 2px solid var(--color-accent)` with `outline-offset: 2px`. Focus outlines are never suppressed.

**State changes are announced.** Dynamic content changes (error messages, loading states, live regions) are marked with `role="alert"` or `aria-live` so screen readers announce them without requiring a page reload. (See Section 9 for a real gap in this principle — `Skeleton`'s loading state currently has no such signal.)

## 2. Semantic HTML Strategy

### Tables
All tabular data uses semantic table elements: `<table>`, `<thead>`, `<tbody>`, `<tr>`, `<th scope="col">`, `<td>`. Div-based table layouts are explicitly forbidden in Atlas. Empty header cells (e.g. for icon-only columns) contain a visually hidden label using the `.srOnly` CSS utility class.

### Forms
All form fields use native `<input>`, `<textarea>`, and `<label>` elements with explicit `htmlFor`/`id` pairing. Custom widgets (e.g. the status dropdown in `TaskModal`/`ProjectModal`) participate in form submission via a hidden `<input type="hidden">` rather than replacing native form elements entirely.

### Lists
Task lists and member lists render as `<ul>` with `<li>` children — never as `<div>` stacks. The `<ul>` carries `aria-label` describing its purpose ("Project tasks", "Loading tasks"). Label/value pairs (e.g. a due date row) use a genuine `<dl>`/`<dt>`/`<dd>` structure — `<dt>`/`<dd>` have no defined meaning outside a `<dl>` ancestor, so a bare `<dt>` without a wrapping list is invalid and must not be used.

### Landmarks
All landmark elements carry `aria-label` values: `<nav aria-label="...">`, `<aside aria-label="...">`, `<header aria-label="...">`. No landmark is unlabeled.

## 3. Keyboard Navigation

### Standard interactions

| Element type | Keys supported |
|---|---|
| Button (`<button>`) | Enter, Space (native) |
| Non-button interactive (`role="button"`) | Enter, Space (explicit `onKeyDown`) |
| Overlay close (backdrop) | Enter, Space |
| Overlay dismiss | Escape |
| Dropdown/menu dismiss | Escape |
| Focus trap cycling | Tab, Shift+Tab |
| Listbox navigation | ArrowUp, ArrowDown, Enter, Space |

### Space key default prevention
All non-button interactive elements call `e.preventDefault()` on the Space key to prevent the page from scrolling while the user activates a control.

### Escape key layering
Where multiple overlay-like components can be open simultaneously, Escape is handled at the innermost layer first. This pattern has grown since Week 5 — `ProjectSlideOver` now guards against **two** possible nested overlays, not one:

1. `StatusField`/`StatusBox` — Escape closes the status dropdown (capture phase, stops propagation)
2. `TaskModal`/`EntityModal` — Escape closes the modal (bubble phase, only fires if the dropdown is not open)
3. `ProjectSlideOver` — Escape closes the slide-over, gated by `!isModalOpen && !isDeleteModalOpen` — every additional nested overlay introduced needs its own guard added here; it isn't automatic.

This layered pattern ensures Escape always closes only the topmost open element.

## 4. ARIA Patterns

### Dialogs (overlays)
All slide-over panels and centered modals use:
- `role="dialog"` applied conditionally (only when open, `undefined` when closed)
- `aria-modal="true"` applied conditionally alongside `role="dialog"`
- `aria-label` or `aria-labelledby` identifying the dialog name
- Focus moved to the first focusable element on open

The conditional pattern (`role={isOpen ? "dialog" : undefined}`) is used because the overlay is always in the DOM (for CSS transitions) but should only be announced as a dialog when visible.

### `EntityModal`'s per-instance `aria-labelledby` (new since Week 5)
`TaskModal` originally used a static `MODAL_TITLE_ID` constant for `aria-labelledby`, which was safe only because a single `TaskModal` was ever the only modal open at once. Once `EntityModal` was extracted as a generic, reusable modal shell — and multiple instances (a task modal, a project modal, a delete-confirmation modal) became able to exist as DOM siblings — a shared static ID would collide and break `aria-labelledby` for whichever instance lost the collision. `EntityModal` now generates its title ID via `useId()` per instance, guaranteeing uniqueness regardless of how many modals are mounted at once. Any new modal built on `EntityModal` inherits this correctly by default.

### Listbox (custom select)
`StatusBox` (the generalized version of what was originally `TaskModal.StatusField`) uses the WAI-ARIA listbox pattern:
- Trigger button: `aria-haspopup="listbox"`, `aria-expanded={isOpen}`, `aria-labelledby` pointing at the visible label
- Container: `role="listbox"`, `tabIndex={0}`, `aria-activedescendant` pointing at the currently focused option's `id`
- Options: `role="option"`, `aria-selected={value === selected}`, unique `id` per option
- Hidden `<input type="hidden">` carries the selected value into `FormData`

DOM focus stays on the listbox container throughout navigation. `aria-activedescendant` communicates the active option to screen readers without moving real focus, which is the standard WAI-ARIA recommendation for listbox widgets. This pattern is now shared between task status and project status via the same generic component — no duplicated implementation to keep in sync.

### Menus (more options)
Note: `ProjectListTable`'s per-row "more options" menu (originally documented here) was **removed**, not just changed — its Edit/Archive/Delete items were unwired placeholders, and once project delete/edit were built as real, working features accessible from `ProjectSlideOver`, the unwired menu became a real UX trap (looked actionable, did nothing) rather than a harmless placeholder. See `docs/decisions.md` context and CLAUDE.md's React Components rules. No menu pattern currently exists in the live app as a result — if one is reintroduced later for a genuinely new capability, document it here fresh.

### Alert regions
Error states and form validation errors use `role="alert"`, which causes screen readers to announce the content immediately when it appears — no user navigation required. Used in `TaskList` (error state), every `EntityModal`-based form's error banner, and the add-member/remove-member inline error messages in `ProjectSlideOver`.

### Visually hidden text
Icon-only buttons and empty table header cells use either `aria-label` on the element or a `.srOnly` CSS class (position absolute, 1px, clipped) to provide screen reader text without visible content. Note: `.srOnly` is currently defined independently in each CSS Module that needs it (no shared global utility exists yet) — functionally consistent, but worth consolidating into a shared module if a third or fourth consumer appears.

## 5. Focus Management

### On overlay open
When any overlay opens (slide-over, modal), focus is programmatically moved to the first focusable element inside the overlay. Implemented via a `useEffect` keyed on the open state, using `querySelector` with the standard focusable selector:

```typescript
'button, a[href], input, select, textarea, [tabindex]:not([tabindex="-1"])'
```

### Focus trap
Focus is trapped inside open overlays so Tab and Shift+Tab cycle within the overlay rather than reaching the inert background content.

**Scope of focus trap:**
- `Sidebar` — mobile only (`window.innerWidth < 1024`).
- `ProjectSlideOver` — always active.
- `TaskModal`/`EntityModal` (and everything built on it — `ProjectModal`, the delete-confirmation modal) — always active.

### Remove-member button swap — observed behavior, not explicitly engineered (new finding, July 2026)
When a user clicks the trash icon on a member row, it's replaced in place by a Cancel/Confirm icon-button pair. **No explicit focus-management code exists for this transition** — no `useRef`+`.focus()` call, unlike the deliberate focus-to-close-button pattern on overlay open described above. Manual testing confirmed that Cancel currently receives focus on the next Tab press, which is the browser's default fallback behavior when a focused element is removed from the DOM (focus reverts toward `document.body`, then Tab resumes from the next element in DOM order). This is **currently working but not guaranteed** — it relies on browser-default behavior rather than an explicit `.focus()` call, and could differ across browsers or assistive-technology combinations. Flagged in Section 9 as a candidate for explicit focus management if this ever needs to be made robust rather than incidentally correct.

### Listbox focus
`StatusBox` keeps DOM focus on the `role="listbox"` container throughout keyboard navigation. Option highlighting is communicated via `aria-activedescendant` rather than moving real focus to individual `role="option"` elements, per WAI-ARIA authoring practices.

### Body scroll lock
Body scroll is locked when any overlay is open, preventing background content from scrolling. `touch-action: none` is applied to backdrops for iOS Safari compatibility. Scroll lock is always restored in the `useEffect` cleanup function. Nested overlays that open inside an already-locked overlay (e.g. `TaskModal` and the delete-confirmation modal inside `ProjectSlideOver`) pass `disableScrollLock` — locking twice is harmless but redundant.

## 6. Overlay & Modal Components

### ProjectSlideOver
- Always in DOM — visibility via CSS (`translateX`)
- `role="dialog"` + `aria-modal` applied conditionally on open
- `aria-label` derived from project name
- Focus moves to close button on open
- Focus trap active always
- Escape closes panel, now gated by `!isModalOpen && !isDeleteModalOpen` (grown from one guard to two — see Section 3)
- Body scroll lock on open
- Backdrop: `role="button"` + `aria-label="Close project details"` + `tabIndex={isOpen ? 0 : -1}`

### `EntityModal` (generalized from `TaskModal`)
- Always in DOM — visibility via CSS (scale + opacity)
- Two-layer positioning: backdrop + centering positioner (`pointer-events: none`, restored by the dialog itself)
- `role="dialog"` + `aria-modal` applied conditionally on open
- `aria-labelledby` via per-instance `useId()` (see Section 4)
- Focus moves to first focusable element on open
- Focus trap always active
- Body scroll lock, `disableScrollLock` prop for nested use
- Backdrop: `role="button"` + `aria-label="Close modal"` + `tabIndex={open ? 0 : -1}`
- `TaskModal`, `ProjectModal`, and the project delete-confirmation modal are all built on this shared shell — accessibility behavior for all three is inherited, not reimplemented per-component.

### Sidebar (mobile)
- On mobile: `role="dialog"` + `aria-modal` + `aria-label="Navigation"`
- On desktop: `role` and `aria-modal` removed
- Focus trap mobile-only, body scroll lock mobile-only
- Escape closes mobile overlay

## 7. Custom Interactive Widgets

### ProjectCard & TaskItem (non-button clickable elements)
Both cards and task rows are `<div>` elements that behave as buttons — not `<button>` elements because they contain nested interactive elements and need layout flexibility `<button>` restricts.

Pattern applied: `role="button"`, `tabIndex={0}`, `onKeyDown` handling Enter and Space (`e.preventDefault()` on Space), `aria-label` describing the action.

### `Avatar` — dual accessible/decorative usage (new, July 2026)
`Avatar` is used in two genuinely different accessibility contexts, and it's worth a future consumer of this component understanding both before adding a third:

- **As real content** — in `ProjectSlideOver`'s member list, each `Avatar`'s underlying `<img alt={name}>` (or initials-fallback text) conveys real information: whose avatar this is. No `aria-hidden` here.
- **As decoration inside an already-labeled group** — in `ProjectCard`/`ProjectListTable`'s capped avatar strip, individual avatars are wrapped in `aria-hidden` spans, because the *containing group* already carries `aria-label="Project members (N)"`. Announcing each individual name again would be redundant noise for a screen reader user who already knows the count and can get full names from the slide-over.

The same underlying component correctly supports both — the accessibility treatment lives in how the *consumer* wraps it, not in `Avatar` itself. Any new usage should deliberately choose one of these two treatments, not default to neither.

### StatusBox (custom listbox)
See [ARIA Patterns — Listbox](#4-aria-patterns) and [Focus Management — Listbox focus](#5-focus-management) above.

## 9. Known Gaps & Future Work

### Screen reader testing
No automated screen reader testing (NVDA, VoiceOver, JAWS) has been performed. Still scheduled, not yet done.

### Color contrast
No formal WCAG contrast ratio audit has been run against the token palette. Still scheduled, not yet done.

### `aria-live` regions
Only `role="alert"` is currently used for dynamic content announcements. More granular `aria-live="polite"` regions for non-urgent updates are not implemented.

### ~~`Skeleton` has no loading-state accessibility signal~~ — RESOLVED
~~`components/Skeleton.tsx` is purely visual — no `aria-busy`, `aria-live`, or `role="status"`. A screen reader user gets no explicit indication that content is still loading during any skeleton state.~~ **Fixed same day as found.** `Skeleton.tsx` now carries `aria-busy={true}` on every instance. Rather than putting `role="status"`/`aria-live="polite"` on `Skeleton` itself — which would cause redundant, spammy announcements when multiple skeletons render together (e.g. the project-grid loading state renders six at once) — those attributes were placed on the *container* wrapping each group: `ProjectList.tsx`'s loading grid, `TaskList.tsx`'s loading list, and `Header.tsx`'s loading branch specifically (not its loaded-content branch, so the live region doesn't linger and cause spurious announcements after the profile loads). Each group now announces its loading state once, not once per skeleton.

### Remove-member focus swap relies on browser default, not explicit management
See Section 5. Currently functional (confirmed via manual testing) but not robust — a `.focus()` call on the Cancel or Confirm button after the swap would make this deterministic rather than incidental. Low priority given it currently works, but a candidate for hardening.

### Date input accessibility
`TaskModal`'s and `ProjectModal`'s due date fields use native `<input type="date">`. Browser implementations of the native date picker vary in keyboard accessibility and screen reader support. A custom date picker may be warranted in a future iteration.

### ~~Timezone handling on date fields~~ — RESOLVED
~~Dates submitted via `input[type="date"]` are converted to ISO strings with `toISOString()`, which outputs UTC. Users in timezones behind UTC may see dates shift by one day.~~ **This was a real bug, found and fixed.** The write path (`new Date("2026-07-31")` parsing as UTC midnight) was never the problem — the display path was: `toLocaleDateString()` formats in the *viewer's local timezone* by default, so a UTC-midnight date-only value displayed to someone behind UTC showed the previous calendar day. Fixed by giving every date-only (non-timestamp) display an explicit `timeZone: "UTC"` in its `Intl.DateTimeFormatOptions`, kept as a separate format constant from genuine instant-in-time values like `createdAt` (where local-time display is correct, not a bug). Full writeup in CLAUDE.md's "Date and Timezone Handling" section.
